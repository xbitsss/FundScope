# Performance record · 2 November 2026

The measurements below are deterministic Node runs on 14,200 synthetic funds. They are useful for comparing the reference filter core with the optimized in-process engine, but are **not** the required 390×844 Chromium run with 4× CPU slowdown. They do not include browser worker serialization, paint, network, heap, scroll frames, INP, or CLS. The before/after runs used different machine load and sample counts, so they should not be read as a controlled speedup ratio.

## Filter baseline and optimized core

| Operation | Reference before p50 / p95 | Reference after p50 / p95 | Optimized engine p50 / p95 |
|---|---:|---:|---:|
| Search keystroke | 489 / 715 ms | 746 / 954 ms | 6.0 / 9.1 ms |
| Category toggle | 294 / 294 ms | 586 / 586 ms | 2.1 / 2.1 ms |
| Metric range | 307 / 307 ms | 666 / 666 ms | 6.5 / 6.5 ms |
| Sort switch | not measured | not measured | 4.3 / 4.3 ms |

The reference after run's slower results reflect both noisy host scheduling and a normalization update; no improvement percentage is claimed. The optimized 14,200-fund index build measured 429 ms p50 (517 ms first run) in the same process. That is above the 150 ms build budget. Search max was 84 ms and sort max 30 ms in this short run; p95 sample counts were 28 for search and 2 for the other operations. These Node values do not prove the phone limits.

Source reports: [`PERF_before.json`](PERF_before.json) and [`PERF_after.json`](PERF_after.json). The script is `node scripts/perf-baseline.mjs` (package alias `pnpm perf:baseline`). It now records the reference and optimized index separately.

## Key derivation

`node scripts/kdf-bench.mjs` on Node v24.15.0 measured five samples per iteration count:

| PBKDF2 iterations | p50 on this host | Rough 4× estimate |
|---:|---:|---:|
| 100,000 | 96 ms | 384 ms |
| 150,000 | 147 ms | 589 ms |
| 200,000 | 189 ms | 757 ms |
| 250,000 | 221 ms | 884 ms |
| 300,000 | 257 ms | 1,029 ms |

The 4× column is only a rough CPU multiplier, not phone emulation. The ETL now uses the required minimum of 100,000 iterations because the higher settings worsen first unlock, while 100-bit generated passphrases provide the primary protection against offline guessing. A real phone benchmark is still needed to determine whether even 100,000 meets the 300 ms KDF target.

## Unlock, mobile and CI limits

- The worker exposes KDF, unwrap, decrypt, and decode phase timings; `?perf=1` shows those phases plus time to the first result window. No throttled browser p95 has been captured, so the ≤1,000 ms unlock objective is not claimed as verified.
- The browser prefetches the manifest/index, decodes v2 columnar data in the unlock worker, avoids whole-catalogue IndexedDB replacement, and persists only the optional device key record. Fund objects are still structured-cloned from the unlock worker and into the screener engine worker; this transfer is not represented in the Node benchmark.
- Playwright is not installed or available in the workspace. `test:e2e`, `test:perf`, the six-viewport mobile audit, scroll FPS, accessibility automation, and low-end heap measurements were not run. No CI performance budget currently fails the build on these measurements.
- Network time for a first visit is outside the app's control. Static service-worker cache can make later visits offline after the needed app and snapshot files have been cached.
